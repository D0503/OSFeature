# 文档质量模型

## 维度与权重

每个适用维度给 0–100 分，再按权重计算综合分；不适用维度从分母移除并重新归一化。评分是摘要，finding 的证据链才是核心。

| 维度 | 权重 | 核心问题 |
|---|---:|---|
| 技术正确性 | 25 | API、参数、返回值、配置和行为是否正确 |
| 版本与兼容性 | 15 | API Level、SDK、设备和废弃信息是否清楚且一致 |
| 完整性 | 15 | 前置、权限、依赖、异常、释放和验证是否缺失 |
| 一致性 | 10 | 页面内部及相关官方页面是否矛盾 |
| 示例可执行性与步骤可复现性 | 15 | 代码能否成立、步骤能否按顺序复现 |
| 表达与信息结构 | 10 | 术语、指代、章节组织和歧义是否影响理解 |
| 链接与资源 | 5 | 关联页、下载、锚点和资源是否有效且匹配 |
| 安全、隐私与合规 | 5 | 权限、密钥、个人数据和危险操作是否处理得当 |

维度建议：100 无可见问题；85 有轻微缺陷；70 有影响使用的缺口；50 有明显错误或多个重要缺口；25 核心流程大面积不成立；0 核心主张错误且不可用。不要因为缺少证据随意给低分；证据严重不足时该维度记 `N/A`。

## 严重度

| 严重度 | 判定 |
|---|---|
| `Blocker` | 会导致核心流程无法执行、数据/安全重大风险，或核心事实与同版本权威证据直接相反 |
| `High` | 会显著误导实现，导致主要功能失败、严重兼容问题或关键前置缺失 |
| `Medium` | 会造成排障成本、部分场景失败或重要理解偏差，但有明确绕过方式 |
| `Low` | 小范围歧义、术语、链接、格式或非关键补充问题 |
| `Suggestion` | 非缺陷的优化建议，不参与缺陷门槛 |

严重度评价影响，而置信度评价证据强弱；二者不能互相替代。

## 置信度

| 置信度 | 条件 |
|---|---|
| `certain` | 同版本直接官方/SDK/可复现证据，且不存在合理替代解释 |
| `high` | 两条以上一致的官方证据，版本基本对齐 |
| `medium` | 有一条相关证据或明确内部矛盾，但仍有版本/上下文缺口 |
| `low` | 主要依赖推断，只适合列为线索 |

`confirmed` finding 通常应为 `certain` 或 `high`。`low` 置信度不得支撑“不合理/高风险”的最终结论。

## 最终结论

| 结论 | 建议条件 |
|---|---|
| `合理` | 综合分 90–100，无 Blocker/High，关键维度均有证据覆盖 |
| `基本合理但需小修` | 75–89，无 Blocker，最多一个非核心 High，问题不阻断主要目标 |
| `需要修订` | 60–74，或存在 High、多个 Medium、关键步骤/版本信息缺失 |
| `不合理/高风险` | 低于 60，或存在 confirmed Blocker，或核心流程被同版本证据证明不成立 |
| `证据不足无法判断` | 正文、目标版本或核心对照证据缺失，无法负责任地评价核心主张 |

门槛优先于分数：confirmed Blocker 不能被其他维度高分抵消；核心证据不足也不能靠语言质量高分得出“合理”。

## Finding 合并规则

- 同一根因影响多个段落时合并为一个 finding，并列出多个位置；
- 技术错误及其导致的不可复现通常合并，避免重复扣分；
- 版本差异与真正错误分开；
- 纯编辑建议不升级成技术缺陷；
- 每个 finding 的建议应直接处理根因，不只改写表面症状。
