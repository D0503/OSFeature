# 验证闭环工作流

## 工程整体接入覆盖

整体接入沉浸光感时，逐实例清单是覆盖核对依据。默认开启组件也需导航到实际页面或触发弹窗、菜单、Toast 后验证；不能用首页截图或全局 ENABLE 代替其他组件证据。所有候选均有处理结论才算完成盘点，仍待核对或未验证时明确覆盖限制，不宣称全量效果通过。

在最终报告的“改造汇总”中简要列出覆盖情况：组件类别、已盘点位置、处理结论、未覆盖原因。已实际改造项沿用逐项结果；默认开启无需修改、不适用和待核对项也说明去向，不伪造修改文件。详细工作清单留在临时目录，最终仍只交付原 Markdown 报告及引用截图。

## 执行顺序

1. 保存改造前 SDK、compile/target/compatible API 和源程序状态证据；按实际修改填写改造记录，不从接入后工程反推改造前版本。按页面与组件拆分改造项。沉浸光感中，悬浮 Tab、各页列表补偿、设置页标题栏、Toast 和菜单分别记录，不能把多个独立效果合成一个“全量材质”目标。
2. 运行 `verify-development.mjs`，内部复用现有静态检查。SDK 或静态检查明确失败时停止构建；`warn` 保留为待核验项，不写成通过。
3. 自动传入 `--execute-build`，按现有 product/module/build-mode 运行 ohpm 和 Hvigor，同步与打包使用 `--no-daemon`。失败保留首个失败阶段与日志，不修改签名或工程配置以绕过失败。
4. 目标设备明确时自动传入 `--execute-run --device <设备>`，安装本轮构建产物并启动。未指定设备时先查询可用设备，多设备需明确选择，不任意安装，不创建或下载模拟器。智感握姿的视觉验证只能使用真机；执行器解析设备信息识别到模拟器时不采集、也不接受导入截图。
5. 根据实际导航填写步骤，最后一步必须断言目标页；到达后采集截图、组件树和运行日志。导航失败不得使用其他页面截图判定目标效果。
6. AI 实际读取证据并对照能力包后补录判定。能力查询启动时机、滚动末项可达、交互回退等动态行为需要运行观察，单张静态图不能证明。
   必须尝试用当前可用的图片读取工具打开截图后再判定；读取失败时准确记录失败原因。截图中的几何布局、实际材质观感与动态交互分开判断；没有错误日志只能作为辅助信息，不能推导材质生效或作用域合法。一个页面的截图不能验收其他页面、未弹出的浮层或未操作的列表。
   悬浮 Tab 必须逐个一级页及内部可切换列表验证滚动开始、过程中内容经过栏下、滚到末尾和末项操作；同时核对补偿只归属于真实滚动容器。未执行这些步骤时，对应运行与视觉结论保持未确认，不得以截图成功补录 passed；发现列表外固定空白或内外重复补偿时填 failed，修复并重新采集证据。各窗口模式分别记录，不能以默认页代替全部页面。
7. 输出一份 Markdown 与其截图附件。编译通过不代表视觉通过；低版本、不支持、关闭、设备算力、系统设置和性能未覆盖时明确标记未验证，所有回退条件与实施前源程序状态基线逐项对照。

## 命令

```text
node scripts/verify-development.mjs --project <工程> --feature immersive-light --route arkui --goal <目标> --changes <改造记录.json> --sdk <SDK目录> --product <产品名> --module <模块名> --build-mode debug --execute-build --execute-run --device <设备> --navigate <导航.json> --capture-screenshot --capture-layout
```

- `--route` 明确为 `arkui` 或 `hds`，组合路线和多个目标顺序执行，汇总到同一报告。
- `--product`、`--build-mode` 默认 `default`、`debug`，执行前核对工程；省略 `--module` 构建整个产品，运行模块须能唯一确定。`--ability` 指定启动 Ability，`--bundle` 限定运行日志所属应用。
- `--import-screenshot <路径>` 可重复传入开发者按引导在真机采集的 PNG 截图，随新运行或与 `--resume` 组合为已有运行补挂截图；导入后仍须由 AI 实际阅读并补录视觉判定。
- SDK 自动定位规则沿用现有工程检查；无法定位时显式指定 `--sdk`。
- 未传执行开关仅检查并报告。实施代理须主动传入具备条件的执行开关；运行只使用本轮成功构建的产物，不使用旧包绕过失败。
- 默认输出 `<工程>/os-feature-integration/integration-report.md`，`--output` 可覆盖目录。
- stdout 返回报告路径、`runId`、临时证据路径及哈希。退出码 0 表示没有确定失败（仍可能未验证），1 表示存在失败，2 表示输入或执行器错误；不能仅凭退出码验收。

## 改造记录

实施代理在系统临时目录准备输入，不把过程 JSON 放进交付目录。以下内容须按真实改动和证据填写：

```json
{
  "schemaVersion": "1.0",
  "id": "home-floating-tabs",
  "page": "首页",
  "component": "Tabs",
  "category": "悬浮 Tab",
  "effect": "底部 Tabs 配置悬浮样式与系统默认材质",
  "files": ["entry/src/main/ets/pages/Home.ets"],
  "before": { "sdk": 26, "compile": 26, "target": 26, "compatible": 23 },
  "fallback": [
    { "condition": "low-api", "behavior": "保留原导航布局、交互与普通样式", "status": "not_run" },
    { "condition": "unsupported", "behavior": "保留原组件状态和普通样式", "status": "not_run" },
    { "condition": "disabled", "behavior": "保留原普通样式与交互", "status": "not_run" }
  ]
}
```

每条记录只覆盖一个可独立验证的页面/组件改造项，列出该项实际修改文件。`effect` 只描述已经实施的代码配置，例如“列表已添加尾部补偿，滚动效果待验证”，不得把预期效果写成验证结论。应用级 ENABLE 单独作为配置记录；具体组件是否生效仍需分别验证，不能据此宣称全量覆盖。

`id` 是推荐填写的稳定改造项标识，同一位置重验或修改目标标题仍使用同一个值；同页不同组件或同类组件的不同实例使用不同标识。旧输入未提供 `id` 时，按 `page + component` 精确匹配，保持这两个字段稳定；不按目标文案或修改文件列表去重。无法精确识别的旧记录不作模糊合并，实施代理须核对原位置并使用一致标识重验。

版本无法确认填 `"unknown"`。回退状态允许 `passed`、`failed`、`not_run`、`not_applicable`；除 `not_run` 外须填写 `evidence`，说明实际证据或不适用依据。

## 导航与采集

```json
{
  "schemaVersion": "1.0",
  "steps": [
    { "stepId": "open-benefits", "action": "tap", "locator": { "by": "id", "value": "benefit-tab" }, "expectPage": { "by": "id", "value": "benefit-page" } }
  ]
}
```

支持 `launch`、`tap`、`swipe`、`input`、`wait`。定位与页面断言为 `{ "by": "id|text|type", "value": "精确值" }`，点击和输入定位必须唯一。`swipe` 使用 `direction`（up/down/left/right）或 `from/to` 两点坐标；`input` 使用 `value` 和可选 `locator`；`wait` 使用 1～30000 的 `timeoutMs`，等待后仍须用实际页面断言确认，不能以固定等待代替启动就绪条件。最后一步必须有 `expectPage`。

## 补录判定

实际阅读本轮证据后填写：

```json
{
  "schemaVersion": "1.0",
  "runId": "本次运行ID",
  "goal": "与本次目标完全一致",
  "visual": { "status": "passed", "summary": "实际观察到的目标特性效果及对应检查项", "evidence": [{ "id": "截图证据ID", "sha256": "本次截图哈希" }] },
  "runtime": { "status": "inconclusive", "summary": "已观察的交互和仍待确认项", "evidence": [{ "id": "运行日志或组件树证据ID", "sha256": "本次证据哈希" }] },
  "staticReview": { "results": [{ "id": "静态warn项ID", "status": "passed", "note": "复核结论与代码依据" }] }
}
```

```text
node scripts/verify-development.mjs --project <工程> --resume <runId> --judgment <判定.json> [--output <原输出目录>]
```

补录只更新报告，不执行构建或设备操作；`--resume` 也可以只导入开发者真机截图或与判定同时提交。视觉判定必须引用本轮截图；运行判定须引用本轮日志或交互组件树。过期运行、其他目标或哈希不符的证据均拒绝。状态允许 `passed`、`failed`、`inconclusive`，没有实际依据时保持未确认。视觉通过不能覆盖静态 `warn`。构建未通过时不能补录任何效果判定；安装与导航未通过时，仅全部引用开发者真机截图的视觉判定可以补录，运行判定一律拒绝。

`staticReview` 用于补录静态 `warn` 项的复核结论：`id` 必须是本次报告中存在的 warn 检查项，`status` 只允许 `passed`（复核无问题）或 `failed`（确认缺陷，需修复后重验），`note` 必填并写明代码依据。复核按检查项 ID 在整个工程的所有改造项上生效并在此后重验中继承；`fail` 级发现不接受复核补录，必须修复。仅包含 `staticReview` 的补录不要求构建或安装已通过。所有 warn 项复核通过后静态检查才标记通过。

`summary` 用简短中文说明本改造项实际观察到的结果、尚未覆盖的内容及限制；证据 ID 和哈希只放在 `evidence` 字段，正文不堆放 E 编号、日志原文或设备 JSON。几何参数仅支持布局结论，材质观感需实际判图；存在未验证要求时不得整体写成通过。

## 智感握姿视觉验证（仅真机）

- 智感握姿的视觉验证只能使用真机。执行器会解析目标设备信息识别模拟器；检测到模拟器时不采集截图、也拒绝导入截图，视觉验证保持未验证并注明原因，报告设备行标注模拟器。
- 握持手、操作手和原生跟手都需要真实的人手握持与触控，自动化点击、滑动或模拟器静态画面均不能作为视觉证据，也不能据此补录 `passed`。
- 验证动作由开发者本人完成：先向开发者说明所选路线的触发条件，引导其依次做出左手、右手、双手或未握持等姿态，等待 UI 变化稳定后再取证；AI 不得以自动化输入替代开发者动作。
- 证据两条路径任选其一：
  1. 引导后截图：开发者保持目标握姿时用 `--capture-screenshot` 采集当前真机画面，随后按常规补录判定；
  2. 开发者选择真机效果：开发者按引导自行截图后，用 `--import-screenshot <路径>` 导入（可重复传入多张，也可用 `--resume` 为已有运行补挂），AI 实际阅读导入截图后补录视觉判定。导入前必须与开发者确认截图来自本轮构建安装的真机目标页面。
- 导入截图在报告中的来源标注为开发者真机采集；以其补录视觉判定时只要求本轮构建通过，安装与导航未执行按未验证呈现。运行判定仍需安装、导航与日志证据。执行器截图与导入截图混合引用时不享受该豁免。

## 结果与存储

- 最终只交付改造汇总、特性类别或路线与模式、视觉验证结果、升级与兼容四部分组成的 `integration-report.md`，以及它引用的 `evidence/*.png`。不生成 JSON 汇总报告。
- 日志、组件树和合并状态存放在系统临时目录 `harmonyos-os-feature-verification/`。清理临时记录后 MD 与截图仍可独立阅读，但不能补录原运行；需要重验时指定新输出目录，避免覆盖无法合并的旧报告。
- 同工程、特性、路线、产品、构建模式、模块下，按稳定改造项标识更新当前结果，目标标题变化不会创建重复项；保留首次已知改造前版本，其他改造项保留。旧格式的同页面/组件重复记录读取时保留最新一项。同一报告顺序写入；不再引用的执行器截图自动清理。
- 最终报告只呈现当前结果，不并列保留同一改造项的历史失败与重验成功。已实施配置、运行验证、视觉验证分列；阶段结果用简短中文，静态提示转为待处理事项并附代码位置，已复核项注明复核结论，完整原始日志留在临时目录。版本任一侧不完整时明确无法确认升级。升级与兼容按整个工程输出一份：版本对照一份，回退表按条件合并所有改造项的保留行为。
- 只有必需阶段及回退检查均通过才标记整体通过；缺条件、未判图或未覆盖场景时保留未确认。

## 平行视界验证

将命令替换为 `--feature easygo-parallel --route router` 或 `--route navigation`，按能力包清单逐项验证。changes.category 记录导航/购物模式，effect 记录实际配置、目标跳转及分栏行为；沉浸光感的材质和悬浮 Tab 专项不适用于平行视界。动态页面、id 归属和系统开关需运行证据，不能因截图命令成功认定分栏正确。
