# 性能、运行与验收

先执行 `verify-integration.mjs --project <path> --feature smart-reach --route <route> --sdk <path>`。auto 只验证已识别的启用路线；没有入口时明确指定路线并复核。三条组合路线分别调用 `verify-development.mjs`，复用 changes、构建、安装、导航、截图和判定流程，汇总为一份报告。

## 静态与构建

- 本机 SDK、compile、compatible、Stage 主模块和实际新增接口门槛一致；不误用 target 或组件早期 since 降低门槛。
- 权限按所属 HAP 和运行 API 核对，每项声明检查 `reason` 字符串资源与 `usedScene.abilities/when`；只有 `ACTIVITY_MOTION` 还需运行时授权。无关模块的权限、注释、测试代码不作为满足证据。库或别名封装未解析时人工沿依赖链核验。
- 原生属性的归属/版本、手动事件的生命周期、同一回调实例与模块权限声明须复核；源文本候选不能证明控制流。
- 未启用/仅 false、仅 off、未检测到封装不能报告完成。warn 项按本轮文件证据复核，不批量改成通过。
- 使用目标工程实际 SDK 构建；本包的静态夹具和示例检查不等于 ArkTS 编译通过。

## 运行与视觉矩阵

| 场景 | 观察与证据 |
|---|---|
| 支持真机左/右切换 | 确认动作信号与 UI 变化对应，记录事件、日志和目标页面截图；原生与自定义分别验证 |
| 新增同步跟手组件模式 | 原组件位置不变；任一入口操作后两组状态、禁用/加载和结果同步，不重复提交；关闭或失败只撤去新增入口 |
| 未识别、双手、未握持、暂时无回调、重复同值 | 已呈现的跟手目标保持当前侧，无归位或重复动画；首次无结果时原组件保持初始位置，新增入口不展示 |
| 明确关闭跟手功能 | 位移模式恢复接入前位置，新增模式仅撤去新增入口；保留业务状态，清空待移位方向，迟到回调不再生效 |
| 按压、长按、拖动中换手 | 目标不逃离，原操作不中断，结束后只应用最新有效方向 |
| 页面切换、遮挡、后台、重复进入 | 无重复订阅、隐藏后不更新 UI、不误删其他组件监听 |
| API 低版本、权限缺失或不匹配、201/801、服务失败 | 完整保留原业务与布局；工程 compatible 低于路线门槛时须在低版本环境实测回退表现并以 `fallback` 判定补录（截图+环境说明），注入异常只证明回退逻辑，不证明硬件表现，也不作为低版本实测的替代证据 |
| 应用关闭、系统关闭、订阅/退订失败 | 无循环重试；对照源基线，无公开查询时记录观测边界 |
| 竖/横屏、手机/折叠屏/平板、窗口尺寸变化 | 在支持设备正常握姿下验证，沿用原断点、安全区和滚动布局 |
| 左右移动动画 | 首次显示从实际初始侧出现，无 `x=0` 占位闪现或横穿；第一次及后续左右换手均核对退场分支从当前侧离开、入场分支从目标侧屏外进入，不能仅凭最终截图断言路径；退出/进入由框架同步过渡，无定时器空档或闪烁；贴边组件等高等边距、组内顺序/间距不变；原按钮可拖动且无新有效方向时须能停在中间；底部栏不遮末项操作区 |

分别读取 [原生](routes/native-component/validation.md)、[操作手](routes/operating-hand/validation.md)、[握持手](routes/holding-hand/validation.md) 的触发条件。操作手需非边缘多次有效触控，握持手需正常接触与亮屏解锁，不能用同一套动作替代验证。

## 真机视觉验证与开发者引导

- 智感握姿的视觉验证只能使用真机。执行器会解析目标设备信息识别模拟器；检测到模拟器时不采集截图、也拒绝导入截图，视觉验证保持未验证并注明原因，报告设备行标注模拟器。
- “仅真机”约束针对跟手/识别**效果**：握持手、操作手和原生跟手都需要真实的人手握持与触控，自动化点击、滑动或模拟器静态画面均不能作为视觉证据，也不能据此补录 `passed`。
- 低版本回退实测验证的是“增强不启用、源基线保持”，不依赖握姿识别硬件，允许使用 API 低于路线门槛的模拟器或真机；按[通用回退实测](../../workflows/verification.md#回退路径实测)执行并以 `fallback` 判定补录，不受本节限制。
- 验证动作由开发者本人完成：先向开发者说明所选路线的触发条件，引导其依次做出左手、右手、双手或未握持等姿态，等待 UI 变化稳定后再取证；AI 不得以自动化输入替代开发者动作。
- 证据两条路径任选其一：
  1. 引导后截图：开发者保持目标握姿时用 `--capture-screenshot --screenshot-scenario <场景>` 采集当前真机画面；基线、左手、右手等状态按[验证闭环](../../workflows/verification.md)用同一 `runId` 的 `--resume` 逐张补采，全部完成后再补录判定；
  2. 开发者选择真机效果：开发者按引导自行截图后，用 `--import-screenshot <路径>` 导入（可重复传入多张，也可用 `--resume` 为已有运行补挂），AI 实际阅读导入截图后补录视觉判定。导入前必须与开发者确认截图来自本轮构建安装的真机目标页面。
- 导入截图在报告中的来源标注为开发者真机采集；以其补录视觉判定时只要求本轮构建通过，安装与导航未执行按未验证呈现。运行判定仍需安装、导航与日志证据。执行器截图与导入截图混合引用时不享受该豁免。
- 屏外进出场须让开发者在真机上观察首次出现、首次换手及再次换手的完整轨迹；可用真机录屏复核。仅有左右终态截图时，报告只能确认落点，动画路径保持待验证。

性能比较接入前后的滚动帧率、换手动画、回调次数与隐藏后的监听活动；以项目已有指标验收，不虚构统一阈值。模拟状态可检查代码分支，但不能替代支持设备上的真实握姿识别效果验证。

验收：各所选路线静态问题已处理、构建通过，运行、视觉与回退项分别有依据；视觉依据仅认可真机证据，低版本回退依据须来自 API 低于路线门槛环境的实测。缺真机/系统信息时报告保留未验证。截图成功、属性存在或 SysCap 为 true 都不是视觉验证通过。
