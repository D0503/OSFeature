# 已接入特性的兼容性扫描与修复

## 任务与边界

用户要求“扫描／检查”时只读工程，输出兼容性扫描报告；明确要求“扫描并修复／补齐兼容性”时才修改目标工程并输出改造报告。只覆盖已注册特性及相关调用，不扩展为全工程 API 审计。无需先指定特性，允许自动发现多个已注册特性；不沿用新接入流程的强制升级和选路步骤。

1. 运行 `node scripts/audit-compatibility.mjs --project <path> [--feature <id>] [--sdk <path>] [--product <name>]`。JSON 输出用于定位，不是最终判断。脚本只读，退出码 0 表示候选收集完成，2 表示输入或执行错误，不代表兼容性通过。
2. 对每个命中特性完整读取注册入口、兼容性资料及 `compatibility-audit.md`。核验所有相关文件；脚本使用标识符和导入信号定位候选，可能漏掉别名、重新导出、依赖包封装、动态表达式或应用级默认材质，须沿导入和引用补充盘点。普通 HdsTabs 不能单独证明握姿已接入。
3. 读取根配置中每个 product 的有效 compatible/target/compile，核对模块覆盖、构建模式及本次实际构建 product。脚本列出根级产品上下文，不能代替真实配置优先级分析。记录未知项，不使用 inspect-project 的首个 compatible 值替代多 product 判断。保持原 compatible 值及格式，不通过提高最低版本解决问题。
4. 定位各 product 实际编译 SDK，核对根清单。显式编译版本与活动 SDK 不一致时，不把自动发现的 SDK 声明作为最终依据。SDK 不可用时继续源码盘点，但依赖声明的判断及自动修复暂停，报告缺少的路径或版本证据。

## SDK 与调用复核

- 本流程允许读取 SDK 声明文件。候选索引保留同名声明和多个重载，不直接绑定。沿真实 import、Kit re-export、命名空间、接收者类型及继承关系定位具体符号；声明在候选索引之外时继续定向读取实际声明。
- 核对方法、属性、选项字段、枚举类型及值、对象构造、组件本身的 `@since`；成员缺注解时追溯所属类型并记录依据。多个重载按真实调用签名选择，多个版本标签的语义不明确时标为待确认，不任取最大或最小值。
- 同时记录完整版本和 API 等级，保留补丁门槛；不能用整数 API 26 证明满足 26.0.1。旧平台版本字符串须按工程/SDK 的可靠映射解析，不能把 6.1.0 当成 API 6。无法映射则待确认。
- 对照最低兼容版本判断是否需要版本保护；版本已覆盖只表示无需该版本守卫，不免除能力包要求的设备能力判断。`@since` 也不替代官方 target、模型及设备约束。
- 复核 if/else、提前返回、逻辑短路、常量、封装返回值、跨文件调用和异步回调的真实控制流。错误方向、过低门槛、逻辑或绕过、守卫晚于访问均不能判为已保护。SysCap 不代替版本判断。
- 检查模块加载、静态/成员初始化、组件构建、查询、订阅、更新和清理；包括属性调用本身和提前求值的枚举/配置对象。文件其他位置的判断、注释、字符串、仅导入不是保护证据。
- 对每处输出 `protected`（已保护）、`missing-protection`（缺少保护）、`not-required`（无需保护）、`needs-review`（待确认），附 SDK 声明和源码路径、行号、适用 product、版本门槛、能力条件及回退结论。同一候选下允许记录多项成员或产品结论；候选之外新发现的调用先补充清单，不隐去。

## 修复

只改确认存在的兼容性缺陷，复用等价有效守卫，不为匹配正则改写源码。按共享兼容性模型选择可用于当前编译 SDK 的版本判断接口，守卫本身也须能在目标低版本调用。新特性相关能力条件独立核对。

按能力包策略优先复用已有回退；找不到原实现时使用已确认备选。适配时强调过的组件、属性、布局、断点、安全区、滚动补偿、状态和事件，回退时逐项对照，避免只换组件。独立业务交互不随视觉回退删除。

## 验证与交付

修复后复扫并构建，按现有 verification 工作流安装本轮产物和导航取证；不能仅验证首页。高低版本都必须实际运行。高版本满足增强能力；低版本低于相关门槛但不低于 compatible；多个门槛覆盖中间分支，并验证最低兼容端。若 compatible 已覆盖全部门槛，则在最低受支持版本和较高版本分别运行，不要求安装到不受支持系统。

覆盖增强、低版本回退，以及能力包要求的关闭/不支持路径。握姿、防窥等遵守真机限制。Tab 必须覆盖 lg/xl 侧边栏和窗口缩放，检查首末项、滚动范围、重复间距、选中态、控制器和事件。弹层及控件必须实际触发和操作。

缺少设备、签名、构建工具或 SDK 时保留已完成工作与具体阻断，运行验证标记未完成；不得声称整体通过，不伪造设备、截图或日志。Skill 开发时使用夹具验证扫描工具，不将夹具结果当作用户工程运行证据。

扫描数据和最终报告使用同一轮工程。报告至少包含：范围和各 product 版本、SDK 路径及声明依据、问题和位置、原守卫与回退结论、采用策略、修改位置、用户入口选择、构建与高低版本矩阵及证据、未完成项。只呈现最终结果，不写调试过程。

可用 `--format markdown` 从扫描数据生成报告底稿；AI 复核后通过 `--review <json>` 补录。review 结构：

```json
{
  "mode": "repair",
  "findings": [{
    "candidateId": "扫描输出中的稳定标识",
    "status": "protected",
    "sdkEvidence": ["SDK声明文件:行号、符号、重载及@since"],
    "evidence": ["工程文件:行号、product、控制流与回退依据"],
    "policy": "能力包策略",
    "change": "最终改动及位置",
    "pendingChoice": "尚未确定的入口选择（如有）"
  }],
  "verification": {
    "build": {"status": "pass", "evidence": ["本轮构建日志与产物"]},
    "high": {"status": "pass", "evidence": ["设备、完整系统版本、product、场景及截图/日志路径"]},
    "low": {"status": "not-run", "evidence": []}
  },
  "pending": ["尚未完成的必要验证或判断"]
}
```

报告生成器只检查补录结构，不能认证证据真伪或场景完整性。交付前逐项确认所有候选、补充调用和 product 已覆盖；不得用部分补录或三项 pass 自动推导兼容性全部通过。
