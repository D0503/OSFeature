# 故障排查工作流

先按[任务读取表](../shared/document-loading.md#任务读取表)加载本任务的能力包公共资料和相关路线资料；专项场景继续遵循能力入口。

1. 记录现象、首次出现版本、目标组件、设备、系统设置和复现步骤。
2. 重新运行工程发现、兼容性判断和静态验证，不沿用可能过期的结论。
3. 按版本门禁、模型/module、配置状态、设备能力、属性冲突、性能六类依次排查。
   路由白屏或目标页为空壳时，先对照当前 product 的部署清单核对设备模块集合、版本、目标路由所属模块及导航日志；只诊断时查询并报告缺失模块，不安装或启动应用；已授权修复/部署时才补齐完整部署并重新验证目标页，再依据证据排查业务代码、版本配置和签名。安装成功、首页正常或采集到节点均不能证明目标路由模块已部署。构建日志中的 `ProcessIntegratedHsp` 任务名不能作为 HSP 已合入 HAP 的依据。
4. 每个候选根因必须关联文件证据、运行日志或可复现实验；低证据结论标为待确认。
5. 用户只要求诊断时不修改工程；要求修复时采用最小改动并执行回归。若问题发生在回退路径，先与接入前源程序状态基线比较，避免用另一套临时降级逻辑掩盖回归。
6. 诊断输出证据、根因或待确认项；修复任务另输出实际修复和回归结果。安装、启动、导航等设备变更须属于已授权范围，不能以“只改设备、不改源码”为由越过诊断边界。
