# 工程实施工作流

1. 确认用户明确要求修改工程，并保存实施前的工程发现、兼容性结果和目标代码的源程序状态基线。
2. 完整读取特性实现文档、共享前置条件、安全规则和输出契约。
3. 复用项目现有导航、主题、类型和状态管理；不要创建与现有架构并行的替代体系。
   涉及悬浮 Tab 尾部避让时，修改前逐页记录宿主到真实滚动容器的路径、窗口条件、已有尾部配置和唯一补偿位置；进入子组件检查后再改动，不因外层存在 Scroll 就追加 Blank。优先更新已有尾部配置，禁止列表外固定占位和同一遮挡的内外重复补偿。
4. 先实现版本、设备能力、授权和外部条件保护；回退分支继续使用接入前的组件树或业务路径并保留布局、状态、数据、交互和普通视觉样式，再在增强分支接入新特性。不得为回退路径另造一套与源程序不同的简化实现。
5. 修改后运行 `verify-integration.mjs`，修复确定性失败。
   整体接入沉浸光感时，重新扫描并与实施前逐实例清单核对，补齐新增、遗漏或封装内的实际调用。所有范围内候选都必须有处理结论，待核对项明确保留；不能仅完成 Tabs 与滚动避让、配置应用级 ENABLE 就宣布工程整体接入完成。无需改代码的默认开启组件也必须验证，不强制重复显式配置。
6. 按[验证闭环](verification.md)运行 `verify-development.mjs`，自动执行具备条件的构建、安装启动、目标页导航和截图；缺少 SDK、签名、明确设备或外部权限时记录限制，不绕过。
7. 按页面与组件分别记录改造项并保持标识稳定；阅读每项实际截图、运行日志和能力包规则后补录判定，并沿代码位置复核静态 `warn` 项后用 `staticReview` 补录结论。已实施配置与验证结论分开，应用级开启不能替代组件实际验证；同一项重验更新当前结果。交付一份 `integration-report.md` 和其截图附件，涵盖实际改造、特性类别或路由模式、视觉验证及升级兼容。
