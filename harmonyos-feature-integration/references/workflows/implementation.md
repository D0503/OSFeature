# 工程实施工作流

1. 确认用户明确要求修改工程，并保存实施前的工程发现、兼容性结果和目标代码的源程序状态基线。
2. 完整读取特性实现文档、共享前置条件、安全规则和输出契约。
3. 复用项目现有导航、主题、类型和状态管理；不要创建与现有架构并行的替代体系。
   特性布局改动按能力包的实施前检查执行；悬浮 Tab 见[滚动尾部避让](../features/immersive-light/shared/validation.md#悬浮-tab-的滚动尾部避让)。
4. 先实现版本、设备能力、授权和外部条件保护；回退分支继续使用接入前的组件树或业务路径并保留布局、状态、数据、交互和普通视觉样式，再在增强分支接入新特性。不得为回退路径另造一套与源程序不同的简化实现。
5. 修改后运行 `verify-integration.mjs`，修复确定性失败。
   整体接入按能力包覆盖清单复核，沉浸光感见[整体接入复核](../features/immersive-light/shared/validation.md#整体接入复核)。
6. 按[验证闭环](verification.md)运行 `verify-development.mjs`，自动执行具备条件的构建、安装启动、目标页导航和截图。本次接入引起的检查或编译错误属于实施范围，AI 必须读取失败证据、最小修复并重新验证构建，通过后继续后续验证；不以单次失败结束任务。缺失 SDK、签名、明确设备或外部权限等条件且无法自行解决时，报告具体阻断原因和所需条件，不绕过。
   运行验证使用完整产品构建，按产品配置收集 HAP 和独立部署 HSP，包括未被 entry 显式依赖的动态路由模块。具备条件时走执行器，出现明确工具阻断才转手动；手动安装也须通过相同的产物及设备模块核验，安装成功提示不代表部署完整。
7. 按页面与组件分别记录改造项并保持标识稳定；阅读每项实际截图、运行日志和能力包规则后补录判定，并沿代码位置复核静态 `warn` 项后用 `staticReview` 补录结论。已实施配置与验证结论分开，应用级开启不能替代组件实际验证；同一项重验更新当前结果。交付一份 `integration-report.md` 和其截图附件，涵盖实际改造、特性类别或路由模式、视觉验证及升级兼容。
