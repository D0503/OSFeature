# 《测试用位置能力接入指南》审查报告

## 结论

这份指南不合理，不能作为可执行的接入与验收依据。仅凭文件内部可见内容，就能确认版本范围、权限声明、验证设备和验收标准之间存在直接冲突；示例还缺少 `request` 的定义。由于材料明确声明其为评测构造内容，本报告不把其中任何 HarmonyOS/API 主张视为官网事实，也不判断冲突双方哪一方代表真实平台行为。

**总体严重度：高。** 这些问题会使读者无法确定支持范围和必要权限，并可能在不受支持的环境中进行无效验证。

## 发现

| 严重度 | 问题 | 文件内证据 | 影响与判断 |
| --- | --- | --- | --- |
| 高 | 起始版本自相矛盾 | “约束与限制”称“从 API 13 开始支持”，步骤 1 又称“适用于 API 11 及以上版本” | API 11、12 是否可用无法同时由这两句话成立。读者无法据此设置兼容范围；指南必须统一版本要求。 |
| 高 | 权限名称及授权步骤自相矛盾 | 配置章节要求 `ohos.permission.TEST_LOCATION_A`，并称“无需其他授权步骤”；失败排查却要求确认 `ohos.permission.TEST_LOCATION_B` | 无法判断实际必需的是 A、B，还是两者；“无需其他授权”也没有解释 B 是否为额外声明或运行时授权。按当前步骤操作不能保证具备调用前置条件。 |
| 高 | 支持的验证设备自相矛盾 | 约束称“只能在真机上验证”，验证章节却要求“在任意模拟器中运行” | 两种验证要求不可同时成立。“任意模拟器”还把范围扩大到未给出支持条件的所有模拟器，因此验证路径不可执行或不可信。 |
| 高 | 把构建成功误作功能验证 | 验证章节称“只要工程构建成功就说明定位功能验证通过” | 构建只能说明静态构建环节通过，不能证明运行时调用成功、权限有效、设备支持或返回了有效位置结果。这也与文中“运行以上代码”的表述混淆。 |
| 中 | 代码步骤不完整 | 示例调用 `testLocation.getCurrentPosition(request)`，但全文未定义 `request`，也未说明其类型和必填字段 | 片段无法独立照抄执行；读者无法确认请求如何构造。应补充导入/类型、初始化和合法参数示例。 |
| 中 | 缺少可观察的功能验收条件 | 示例只打印 `result`，没有规定成功判据、必要字段、失败判据或错误处理；验证部分也未要求检查输出 | 即使程序运行，也没有可重复的方式判断“定位功能验证通过”。 |

## 修订要求

1. 选择并统一唯一的最低 API Level，同时说明低版本行为或兼容策略。
2. 明确列出所有必需权限，区分配置文件声明与运行时授权，并使故障排查与接入步骤一致。
3. 统一真机/模拟器支持范围，给出明确设备和环境前提。
4. 补全 `request` 的构造及异常处理，使示例可运行。
5. 将验证改为运行时功能验证：确认调用成功、检查约定的结果字段，并覆盖权限拒绝或调用失败；不能以“构建成功”替代功能验收。

## 证据边界

本结论只依据 `guide-with-internal-conflicts.md` 的内部文本一致性。没有使用外部资料，因此不对真实 API 的版本、权限名、设备支持或返回行为作事实认定。
