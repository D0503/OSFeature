## 4. 问题清单

### DOC-001 最低支持版本在同页互相排斥

- 维度：版本与兼容性 / 一致性
- 状态：`confirmed`
- 严重度：`High`
- 置信度：`certain`
- 原文位置：`约束与限制`（第 7 行）；`开发步骤`第 1 步（第 15 行）
- 原文短摘录：“从 API 13 开始支持”；“适用于 API 11 及以上版本”
- 问题分析：同一能力的最低版本不能在同一适用范围内同时为 API 13 和 API 11；文件未给出场景、重载或设备差异来化解冲突。
- 核验证据：证据 [E1] 的第 7、15 行构成同页内部直接证据链。
- 影响：API 11/12 读者无法判断是否应接入，可能在不支持的目标版本上实施核心流程。
- 修改建议：先用同版本 API 参考或 SDK 核实唯一的起始 API Level，再统一“约束与限制”、步骤和示例配置；未核实前不要保留两个数字中的任一个作为事实。

### DOC-002 权限配置前后矛盾

- 问题分析：前者排除了其他授权步骤，后者却把另一个权限声明作为失败排查条件；未说明两个权限是否替代、并存或按场景选择。

### DOC-003 验证设备与成功判据均不能证明功能成立

- 维度：示例可执行性与步骤可复现性 / 一致性
- 状态：`confirmed`
- 严重度：`High`
- 置信度：`certain`
- 原文位置：`约束与限制`（第 7 行）；`验证`（第 29 行）
- 原文短摘录：“只能在真机上验证”；“在任意模拟器中运行”；“工程构建成功就说明定位功能验证通过”
- 问题分析：真机限定与任意模拟器验证直接冲突；同时，构建成功只表示静态构建阶段通过，不能观察到定位调用是否成功或返回有效结果。后一点是验证逻辑缺陷，不依赖真实测试 API 的行为。
- 核验证据：证据 [E1] 的第 7、29 行给出互斥环境与错误的成功判据。
- 影响：读者可能在文档明确排除的环境中测试，并把未执行或执行失败的功能误报为验证通过。
- 修改建议：统一受支持的验证设备；把成功标准改为可观察的运行结果，并同时记录调用成功、结果校验及失败日志。真实可观察字段需在同版本 API 证据确认后再写入。
- 建议改写：`请在文档确认支持的设备上运行示例；仅当核心调用成功且返回结果满足已定义的校验条件时，才视为功能验证通过。构建成功只作为前置检查。`
